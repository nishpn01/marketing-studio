# Scoped disclosure of restricted sources (`studio.source-disclosure/0.1`)

Status: implemented in the legacy Runner and represented by signed pending requests in the local Service. Default behaviour is unchanged: **a restricted source is refused before any model call** unless a valid grant exists. The CLI and Service have different authority properties; see [current authority status](../operations/AUTHORITY-AND-CAPABILITY-STATUS.md).

## What this is not

Every actor here is a **local, unauthenticated assertion**: the "owner" text, the "host" name and the operator running the CLI are labels, not verified identities. Anyone with filesystem access to the workspace can edit sources, session records, grants, markers and the ledger, run the model themselves, or read the restricted file directly. Nothing below defends against that. This is a guard against accidental or model-side over-disclosure and a tamper-evident record, not production access control. Remote or multi-user use needs authenticated authorization and OS-level isolation first.

## Threat model

In scope (the Runner must not do these):
- send a whole restricted source, its provenance header, redaction text or the owner's grant quote to a model role;
- reuse a grant after the source changed, was revoked, expired, or for another workspace, copy, session, host, role or purpose;
- let a copied or edited header, session record or request flag downgrade a source to approved;
- put restricted text into receipts, logs, artifacts, review packages or error messages beyond what the grant permits;
- treat `drafting` consent as consent to `publication`.

Out of scope: a malicious local user, a compromised host model that already holds the text, text already shown to a model (it cannot be recalled), and what a role does with the excerpt it legitimately received (a writer may quote it in a draft; fact QA still caps claims verified only by a restricted source at `private_approval_required`).

## The grant

A JSON file in `.studio/source-disclosures/<grant-id>.json` plus a hash-chained, append-only `audit.jsonl` (shared code with capture disclosure, `src/disclosure-ledger.ts`). The ledger records the grant file's sha256; a revocation writes a marker file and a ledger event (so losing the ledger tail does not un-revoke).

It binds: workspace id and resolved workspace root hash, exact `source_path`, `source_sha256` of the whole file (version-bound), `session`, asserted `host`, `roles` (any of `director`, `writer`, `fact_reviewer`, `craft_reviewer`), `purpose`, exact `excerpts` (1-5, each 8-2000 characters, 6000 total, distinct, and each must occur **literally in the source body**, not the provenance header), optional `expires_at`, optional `direction_sha256` (grant input `bind_direction: true` pins the session's currently approved `direction.json`, so a new direction needs a new grant), and `owner_authorization` (the owner's words, stored and labelled `authenticated: false`).

Purposes are separate and never imply one another:
- `drafting`: the only purpose the Runner ever requests, for its model roles.
- `internal_read`: recorded, but no Runner path requests it; it never satisfies a run (reserved for host-side reading).
- `publication`: can be recorded, but the Runner never satisfies it. No code path returns a view for it.

## What a model role sees

For each restricted source, `loadSources` classifies the source (workspace registry, session evidence, business catalog, and the file's own header; any one saying restricted wins), then resolves the grants. The full text of a restricted source is dropped; each role gets only `excerpts.join('\n\n')` for its own grant, with no header, no provenance, no owner quote. The craft reviewer never receives sources. A role not covered by a live grant gets nothing and the run is refused (`role_not_granted`). Two live grants covering the same role are refused (`ambiguous`); disjoint grants compose.

The sanitized view is what fact QA checks reviewer excerpts against, so reviewers cannot "verify" a claim against text they never saw.

## Revalidation points

`loadSources` is the single choke point and re-resolves the grants on: run start (before any run row), every model call including retries and receipt reuse (director, writer, fact, craft), resume, revise, approve, `handoff-check` and `handoff-prompt`, and `session-run` / `session-rerun`. The source digest and a signature of the grants that produced each view are pinned in `source-index.json`; a changed grant set blocks later steps like source drift does.

Failures are fail-closed `PERMISSION` errors: `Restricted evidence cannot be sent to model roles: scoped disclosure not valid (<code>)`, where code is one of `no_context`, `no_grant`, `revoked`, `expired`, `stale_source`, `scope_mismatch`, `role_not_granted`, `ambiguous`, `excerpt_invalid`, `purpose_unsupported`, `tampered_or_unavailable`. Codes carry no private text; ledger and grant parse errors are collapsed into `tampered_or_unavailable`.

## Using it

1. Add the evidence (`evidence-add`), approve the direction.
2. Write a grant input file: `workspace_id`, `session`, `host`, `purpose` (`drafting`), `roles`, `source_path`, `excerpts`, `owner_authorization`, optional `expires_at`, `bind_direction`.
3. `source-disclosure-grant --workspace W --file F`; `source-disclosure-list [--session S]` (metadata only, never excerpts); `source-disclosure-revoke --grant ID --owner-quote TEXT`.
4. Start with the same host: `session-run --session S --host H` (also `session-rerun`). Direct `run` requests carry `"disclosure": {"session": S, "host": H}`. The host is asserted at run start and stored in the run's request; resume, revise and approve reuse it.

## Residual risks

### Studio Service authority store (implemented)

The Studio Service path keeps source visibility, direction decisions, disclosure grants and revocations in a per-tenant signed SQLite store outside the copied workspace. Service workers verify the mutually bound record/log set before every authority read; a changed, missing or unsigned row makes the store unavailable. Service MCP exposes pending requests, not authority writes. Service MCP does not expose capture tools; capture visibility still comes from workspace files and stays out of the Service until it is signed. The legacy CLI path above is intentionally unchanged and remains non-authoritative; its VULN-1 and VULN-7b tests stay skipped. Service-path regressions are in `studio-runner/test/studio-service.test.ts`.

**Residual risk until M1.6:** this is not a same-OS-user security boundary. A process running as the same OS user can read the Service data directory and its HMAC key, then forge records. It can also replace the key and store before a Service (re)start, or replay an earlier store or head; mode and owner checks on `authority.key` stop accidents, not a same-user attacker, and M1.6 fixes this. M1.6 must run the Service under a separate OS user before this is used for sensitive tenant data.

### Owner inbox (implemented)

The Service serves an owner inbox at `http://localhost:<port>/inbox`, next to but separate from the bearer-token `/mcp` endpoint. MCP can only create pending requests (`request_direction_approval`, `request_disclosure_grant`). The Service signs a snapshot of each request into the authority store when it is created. The inbox shows exactly that snapshot and its sha256. Approve, reject, revoke, approve-version and revise each need a fresh WebAuthn passkey assertion. Its challenge is derived from the action, the target and the digest of what the page showed. The Service checks origin, rpId (`localhost`), challenge (single use, two-minute expiry), the user-presence and user-verification flags, the signature counter and the registered credential. It then records the decision and its effect atomically, once per request, version or grant. A changed pending file has no effect. A changed signed snapshot makes the store unavailable. A replayed or mis-bound assertion and a second completion are refused. `run_status` reports `ASSET_APPROVED` only from a signed `editorial_approval` whose run id, version and digest match the run's current version and digest, and only while the current draft bytes still hash to that digest. A signed approval that no longer matches is reported as `APPROVAL_NOT_CURRENT`. Inbox routes refuse bearer tokens. They require the `localhost:<port>` Host and Origin, a CSRF token tied to an HttpOnly SameSite=Strict cookie, and JSON bodies. GET never changes state.

The owner registers one ES256 passkey with a single-use setup code that the Service prints to the terminal that started it. The code expires after 10 minutes. Each inbox session gets 5 wrong guesses, so another local client cannot lock the owner out. Typing `setup` in that terminal prints a fresh code and voids the old one, with no restart. Registration stores the key carried in the authenticator's attested credential data (COSE, ES256 on P-256 only) and refuses a supplied public key that differs from it. Whoever sees that terminal can register first, so register before letting agents start or watch the Service. Source classification is not yet an inbox action. Capture visibility stays out of the Service. Revise records the owner's decision and notes but does not start a new run.

**Follow-ups:** signed capture visibility and inbox source classification. M1.6 changes to asymmetric, read-only worker verification and anchors whole-database rollback outside the attacker-writable user context; job-to-run binding also remains to be added.

- On the legacy CLI path, host, owner and operator are assertions. Local filesystem access bypasses the CLI's recorded authority, including rewriting source, session records and grants consistently. The Service path uses a passkey inbox but remains same-OS-user local.
- The ledger is hash-chained, not signed: someone who can write the directory can rebuild it.
- Revocation cannot preempt a model call in flight, and `source-disclosure-revoke` waits for the workspace lock, so it is refused while a run is executing; retry when the run stops (the next call is then refused).
- Disclosed text and any draft that quoted it persist in receipts, artifacts and the review package; those are private run files, not scrubbed on revocation.
- The grant file holds the excerpts and the owner's words in cleartext under `.studio/`; keep `.studio/` out of version control.
- A granted role may paraphrase or quote the excerpt in a draft. Only the owner's later approval decisions control publication, which this Runner never performs.
- Binding is to the workspace's resolved path; moving or copying a workspace invalidates grants (reissue).
- Excerpts are exact substrings; a wider excerpt than intended is possible, so review the excerpt before granting.
- Claim-text grants (a claim without a literal excerpt) are not supported; grant the supporting excerpt instead.
- **Accepted legacy CLI residual, VULN-1 (adversarial report):** `sessions/<slug>/session.json` is the only classification authority for non-catalog host evidence. Someone who can write the workspace can rewrite an evidence header and the session record (visibility and sha256) together and relabel restricted evidence as approved, so no grant is consulted. The Service path does not read workspace authority for its own route.
- **Accepted legacy CLI residual, VULN-7b:** a revoked grant (source or capture) is resurrected by deleting its `.revoked.json` marker and truncating the last audit line, because the legacy ledger head is not stored elsewhere. The Service path keeps its authority store outside the copied workspace, but same-OS-user key/store replacement remains possible until the tracked authority milestone.
- Capture classification now has an anchor under `.studio/capture-anchors/` (VULN-6). It stops the two-file flip inside `captures/`, but a writer who also edits `.studio/` still wins. Captures with no matching anchor are treated as restricted.
- Redaction and heading exclusion are best-effort string/markdown rules. Matching is Unicode-folded per code point (NFKD, combining marks and zero-width/format characters dropped, case-folded, Greek final sigma unified) and whitespace-tolerant; headings ignore emphasis and a trailing colon. **Limits:** a zero-width space or U+180E used *as* the gap between words defeats a multi-word string; `ß` is not equated with `ss`; over-redaction happens at code-point granularity. A configured `exclude_headings` entry that matches no section **fails closed** at `evidence-add` and `context-sync` (generic error); `context-search` simply **omits** that document, with no error or warning. A section ends only at an unambiguous ATX heading of equal or higher level (not indented 4+, not in a code fence or HTML comment); setext headings can start an exclusion only over a plain paragraph line, and a fence closer with an info string does not close the fence. When in doubt the parser keeps excluding, so it may withhold more than intended. Excluding a section and its own subsection works in either order. This is still a best-effort parser, not a CommonMark implementation: partial exclusion from constructs not listed here is possible, so do not treat `exclude_headings` as a guarantee.
- Default capture redaction (phones, JWTs, common key prefixes, obfuscated emails) is pattern-based and incomplete. Email and obfuscated-email scans are linear-time manual scans and the `claude-code-jsonl` block stripper is linear; heading parsing (catalog evidence only, not capture import) is hand-written with line caps. Profile redaction applies to message text, capture titles and annotate paraphrases; quotes must be verbatim from already-redacted messages.
- The offline mock runner now also refuses unclassified sources; only fixture tests set `STUDIO_ALLOW_UNCLASSIFIED_MOCK=1`.

## Additional documented limits (independent review, F-* findings)

- **Scoping covers the raw source, not derived text.** A role not named in a grant never receives the source, but text the writer legitimately quotes flows on by design: the **craft reviewer** receives the draft, and the **handoff reader** receives the run snapshot and review package (which can contain claim text for `private_approval_required` blockers). Grant only excerpts you accept appearing in a draft and its review package.
- **Anchors and ledgers are tamper-evident, not tamper-proof (F-CAP-1).** The capture classification anchor and the `record.json` anchor are unkeyed hashes of values that appear in the repository. They catch accidents and one- or two-file edits inside `captures/`; anyone who can read this code and write `.studio/` can recompute them. Same trust level as VULN-1 and VULN-7b. Keying them needs a secret held outside the workspace.
- **Approvals are unauthenticated and script-satisfiable (F-APPROVE-1, F-FLOW-1).** `approve`, `improvement-decide`, `direction-approve`, `source-disclosure-grant`, `evidence-add --owner-quote` and `capture-import --authorization` record words, not identities. A script that can read the run folder can build a valid `decisions.json` and approve; nothing publishes, and the record says `authenticated: false`. The only guard against an agent doing this is the host skill text ("never approve for the owner"). Add host permission rules that deny those commands unless the owner confirms interactively. If the deployment widens to remote, multi-user, or an agent the owner does not fully trust, this becomes a blocker.
- Grants now expire after 30 days unless `expires_at` is earlier or the input sets `no_expiry: true`. They are still not use-counted and not bound to a particular idea or run; `bind_direction` narrows them to one approved direction.
- Each owner revision adds a bounded allowance (6 model calls, 6 steps) on top of the request budget, so a revision cannot strand a reviewed draft in `BLOCKED_BUDGET`. The request budget therefore covers the **first pass only**; the hard ceiling per run is the request budget plus 5 owner revisions (`MAX_OWNER_REVISIONS`) times the allowance. A sixth revise is refused with a clear error and leaves the run approvable. Revisions are as unauthenticated as approvals.
- Registry prompt and skill paths must resolve inside the repository (`STUDIO_ALLOW_OUTSIDE_ROLE_PATHS=1` lifts this for trusted launchers and tests). `STUDIO_ROLES_FILE` and `STUDIO_CLAUDE_BIN` are refused unless `STUDIO_ALLOW_ENV_OVERRIDES=1`, because they redirect which instructions and which executable receive every prompt. Symlinks inside the repository are not resolved by this check.
- Source text, provenance, drafts and the handoff files placed in prompts have the Runner's own tag names (`source`, `provenance`, `draft`, `skill`, `file`, `workspace_context`, `claims`, `brief`) escaped, and the `path` attribute is quote-escaped. Workspace-context text in the system prompt is escaped for `workspace_context`, `skill`, `source`, `draft` and `file`. Model-produced JSON (brief, claims) is interpolated raw after the blocks it could forge, and fact verification is re-checked against the real source text. Other markup in sources is left alone.
- Handoff briefs strip embedded credentials from the git remote URL (`https://user:token@host/...`); other free-text fields (`finding`, `proposed_change`, `idea`, notes) are sent as given.
- **Pinned rules and uncommitted edits.** `skill_pins` now records `git status --porcelain` for the pinned prompt, skill, contract and registry files. A new run (`run`, `session-run`, `session-rerun`) is refused while any is uncommitted unless `--allow-dirty-pins` is passed; the opt-in is recorded as a `dirty_pins_allowed` event and the review package prints "UNCOMMITTED CHANGES in pinned rules". Resume and approve of existing runs keep the digest-drift behaviour. `improvement-close` treats a change as in effect only when the recorded commit SHA is reachable from HEAD and pinned files are clean; a PR URL, a file path or "present in this checkout" proves nothing.
- A run replaced by `session-rerun` or a new direction is marked superseded and can no longer be resumed, revised or approved (its files remain). If a revision reproduces byte-identical text, the earlier digest still approves the new version; the owner may have read a different package. Not changed.
- **Opus review items not fixed:** `recoverStale` checks the lock outside the lock, so two racing `session-run` calls can both pass recovery (history can be lost; approval is not bypassed); `session.json` has no lock of its own; `STUDIO_ALLOW_OUTSIDE_ROLE_PATHS` and `STUDIO_ALLOW_UNCLASSIFIED_MOCK` do not require the master override flag, and all of them protect only against a stray variable, not against whoever controls the environment; symlinks inside the repo that point outside are followed by role-path confinement; `redactAll` does not equate `ß` with `ss` or treat zero-width characters as word gaps; free text typed into `idea`, direction notes, feedback and improvement text goes to roles and briefs unfiltered.
- **Final-diff review fixes and their limits.** The heading scanner is CRLF-tolerant, treats `<!--` as a comment only at line start, ends a section only at an unindented ATX heading outside fences, comments and raw HTML blocks, and withholds the document (fail closed) if any surviving line still reads as an excluded heading. That post-check is deliberately blunt: a plain line that equals an excluded heading text is also a reason to withhold. A setext heading over a paragraph that starts with `<` or `|` is recognised only as part of the whole paragraph, so it may be withheld rather than excluded.
- **Dirty-pin detection** compares each pinned file's bytes with `git cat-file blob HEAD:<path>` (so `assume-unchanged` and `skip-worktree` are caught) and treats git being unavailable or failing as dirty, which needs `--allow-dirty-pins`. The gate and the recorded `skill_pins` event use the same computed list. Limits: `core.autocrlf` conversion is not exercised and may report CRLF checkouts as dirty (fails closed); `changeInEffect` checks only the global role pins, not a specialist's, and accepts any ancestor commit, including one that a later commit reverted; `--allow-dirty-pins` is read from the command line as an exact flag token and is never a request-file, environment or MCP setting.
- **Prompt escaping is a heuristic.** The Runner's own tag names are escaped (`<source`, `</source`, etc.), but variants such as `< /source>`, a zero-width character inside the tag name, full-width `＜/source＞` or a literal `&lt;/source&gt;` are not rewritten. Nothing parses the prompt, so these cannot change Runner behaviour, but a model may read them as tag boundaries.
- A `session-rerun` supersedes the earlier run only after the replacement run exists; a rerun refused for dirty pins, changed evidence or a provider/context failure before the run row leaves the earlier run approvable and the session linked to it.
